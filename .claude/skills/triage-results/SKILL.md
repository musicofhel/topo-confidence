# /triage-results

Read completed experiment results, identify which succeeded, and propose
follow-up experiments in different directions. Writes candidates to a staging
file for human review before anything enters the research graph.

## When to invoke

After `python -m pipeline run --local` completes a batch, or any time you want
to triage a set of completed experiment results. Called from `/session-loop`
during the TRIAGE stage.

## Inputs

Either:
1. A specific result brief: `/triage-results briefs/result-*.md`
2. A specific results.json: `/triage-results pathway11_h100/spectral_alpha/results.json`
3. No arguments: scan for all un-triaged results (see "Auto-scan" below)

## How it works

### Step 1: Gather results

If given a specific file, read it. Otherwise, auto-scan:

```bash
cd ~/topo-confidence

# Find result briefs generated by the pipeline
find research-graph/briefs -name "result-*.md" -newer .claude/session-state.md 2>/dev/null

# Find results.json files modified since the session started
find data/ pathway11_h100/ -name "results.json" -newer .claude/session-state.md 2>/dev/null
```

If no session-state.md exists, fall back to results modified in the last 7 days:

```bash
find data/ pathway11_h100/ -name "results.json" -mtime -7 2>/dev/null
```

### Step 2: Read and classify each result

For each results.json, extract the key metrics and classify:

| Classification | Criteria | Action |
|---|---|---|
| **HIT** | `target_met: true` OR AUROC >= 0.75 OR significant improvement over baseline | Propose follow-up directions |
| **NEAR-MISS** | AUROC in [0.60, 0.75) OR within 0.02 of target. Check per-feature breakdown — a strong individual feature (>0.70) upgrades from NULL. | Propose targeted refinements |
| **NULL** | AUROC < 0.60 AND no individual feature above 0.65 | Log as negative result, no follow-up |
| **INCONCLUSIVE** | High variance, too few samples, or confounded | Propose replication with fixes |

For result briefs (`.md` files), read the YAML frontmatter `outcome` field and
the "Result JSON verification" section to get the same information.

### Step 3: Generate follow-up proposals

For each HIT or NEAR-MISS, propose 2-3 follow-up directions. Each proposal must:

1. State which result it builds on (by FE ID or experiment path)
2. Describe what to try differently (ablation, hyperparameter, different layer, etc.)
3. Estimate whether it's local-runnable (2060 Super + CPU) or needs cloud GPU
4. Give a rough time estimate (minutes/hours on local hardware)

Follow-up direction categories:
- **Ablation**: Remove one component to test if it's load-bearing
- **Scale**: Try different problem counts, layers, or features
- **Transfer**: Try the same approach on a different model or benchmark
- **Combine**: Merge this result with another finding
- **Refine**: Tune hyperparameters or preprocessing

### Step 4: Write staging file

Write all proposals to `.claude/triage-staging.md` in this format:

```markdown
# Triage Results — {date}

## Session: {batch_id from session-state.md}

## Summary
- Triaged: N experiments
- Hits: N
- Near-misses: N
- Nulls: N
- Inconclusive: N

## Hits

### {FE-ID or experiment path}
**AUROC**: {value} | **Target**: {target} | **Met**: {yes/no}
**Key finding**: {one sentence}

#### Proposed follow-ups
1. **{direction-type}: {short title}**
   - What: {description}
   - Why: {rationale}
   - Local-runnable: {yes/no}
   - Est. time: {estimate}

2. ...

## Near-Misses

### {FE-ID or experiment path}
...

## Nulls (no follow-up)

### {FE-ID or experiment path}
**AUROC**: {value} | **Reason**: {why it's null}

## Inconclusive

### {FE-ID or experiment path}
**Issue**: {what went wrong}
**Proposed fix**: {what to change for replication}
```

### Step 5: Update session ledger

After writing the staging file, update the session state:

```bash
cd ~/topo-confidence && .venv/bin/python -c "
from pipeline.session_state import load, save
s = load()
s.notes = 'Triage complete. Review .claude/triage-staging.md before advancing.'
save(s)
"
```

Do NOT advance the stage automatically. The human reviews the staging file
first, then `/session-loop` advances to PLAN_V1.

## Constraints

- **Local compute only.** 2060 Super + CPU. Any follow-up requiring cloud GPU
  must be flagged as `Local-runnable: no` with a note about what hardware it needs.
- **No auto-promoting to research graph.** This skill writes a staging file.
  Promotion to `:FutureExperiment` nodes happens only after human review.
- **Check FINDINGS.md before proposing.** Don't propose experiments that
  duplicate existing findings F-1 through F-10.
- **Check NEXT_EXPERIMENTS.md before proposing.** Don't propose experiments
  that are already in the queue.
- **Reference the research graph.** Before claiming a direction is novel:
  ```bash
  cd ~/topo-confidence/research-graph && python query.py novelty "<claim>"
  ```

## Example

Given `data/experiment1/results.json` with AUROC 0.6993 and target 0.75:

- Combined AUROC 0.6993 is in [0.60, 0.75) → **NEAR-MISS** by default
- Per-feature check: H0_n_features at 0.7219 > 0.70 confirms NEAR-MISS
  (strong individual feature despite weaker combined score)
- Follow-up: try dropping weak features (H1_max_lifetime at 0.598) and
  refit with only the top 3 features
