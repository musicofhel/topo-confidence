# Triage brief — 2409.13714 — TracrBench: Generating Interpretability Testbeds with Large Language Models

Source: https://arxiv.org/abs/2409.13714
Triaged: 2026-04-29

## Refutations

TracrBench is a *testbed* paper, not a results paper, so direct refutations are
indirect: they fire only if our methods are applied to TracrBench's
compiled-transformer models and fail. The pathways below are nonetheless
falsifiable by a concrete experiment — running our existing probes against the
121 TracrBench models with their ground-truth circuit annotations.

1. **Against F-2 (Prefill L19 DoM is a strong correctness predictor).**
   Mechanism: if a DoM-style mass-mean probe is applied to TracrBench compiled
   transformers performing a binary RASP task with a *known* ground-truth
   discriminative circuit, and the probe direction cosine-aligns weakly (cos <
   0.3) with the ground-truth feature subspace, then F-2's interpretive frame
   ("DoM picks up a computationally meaningful direction") collapses into
   "DoM picks up a training-dynamics-correlated direction that happens to
   correlate with correctness in trained natural-language LMs but does not
   recover circuits where they exist." Falsifiable: take 5–10 TracrBench
   programs with binary outputs, fit DoM at the residual-stream layer Tracr
   compiles the decision into, compute cos(DoM, ground-truth feature axis from
   RASP→weight mapping). Cos near 0 refutes.

2. **Against F-10 (Persistent homology on trained residual streams is at the
   Gaussian null).** Mechanism: F-10's interpretation hinges on PH being a
   weak detector — *anything* on natural-trained LMs lies in the Gaussian
   regime. If we run the same H_0 / H_1 PH pipeline on TracrBench residuals
   (whose weights *encode finite-state symbolic algorithms* and whose
   activations are by construction non-Gaussian discrete-symbolic), and PH
   *still* lands at the Gaussian null, then the null is not a property of
   "training erases topology" — it is a property of the PH protocol itself
   (Vietoris-Rips on standardized residuals). That partially refutes the F-10
   write-up, which currently leaves room for "richer / unbatched / non-trained
   datasets might escape the null." Falsifiable: PH on Tracr-compiled
   activations from ≥20 programs; if same null, F-10's mechanism statement is
   PH-protocol-bound, not training-bound.

3. **Against H-13 (Head-level attribution of prefill vs final-token
   circuits).** Mechanism: H-13 assumes that decomposing residual-stream
   activity into per-head contributions and projecting onto DoM directions
   recovers a meaningful "prefill circuit head" vs "final-token circuit head"
   split. TracrBench gives us ground-truth: each compiled transformer has a
   known head→RASP-primitive mapping. If we apply DoM-projection head
   attribution to a TracrBench transformer that solves a two-stage program
   (e.g. "find max then count"), and the attribution does not concentrate on
   the heads Tracr explicitly compiled the relevant primitive into, then the
   head-attribution methodology behind H-13 fails its only ground-truth test
   and the experiment plan needs revision before any compute is spent on
   Qwen-2.5. Falsifiable: pick 3 multi-stage TracrBench programs, run
   DoM-projection attribution, compare head ranking against the known Tracr
   compilation map.

## Direct connections to F-N / H-N

- **F-2 (Prefill L19 DoM AUROC 0.7731, OOF 5-fold)** — TracrBench provides
  the only available ground-truth substrate where one could ask "does the
  DoM direction recover the actual circuit?" — see Refutation 1.
- **F-3 (cos(prefill_DoM, final_DoM) = 0.046, orthogonality)** — TracrBench
  could test whether *deliberately compiled* multi-stage programs exhibit the
  same prefill/final orthogonality. If a Tracr program with a single-head
  read-out shows F-3-style orthogonality, F-3 reduces to "two distinct
  positions read different subspaces" rather than "prefill and final
  computations are mechanistically independent."
- **F-10 (PH at Gaussian null)** — see Refutation 2.
- **H-13 (head-level attribution)** — see Refutation 3. TracrBench is the
  natural ground-truth validation step before running H-13 on Qwen.

No direct headline-number anchor (AUROC 0.7731, cos 0.046, peak PR 67/88,
71.6% selective-prediction accuracy) is challenged by anything *measured* in
the paper itself; the paper only releases programs and weights.

## Methodologies extracted

- **LLM-assisted dataset bootstrapping (20-shot prompt, best-of-5 sampling,
  human validation).** *Replication cost*: ~1 day API spend if we ever needed
  to expand TracrBench-style coverage. *We'd plausibly run this*: no — we
  don't generate datasets, we extract activations.

- **Tracr (RASP→weights) compilation as a probe-validation harness.**
  *Replication cost*: 1–2 days, library is publicly released
  (github.com/google-deepmind/tracr); pure-CPU. *We'd plausibly run this*:
  yes, as a low-cost ground-truth check on DoM-projection probes (motivates
  P11-FE73 below). The chief value: fixes the "we have no oracle" gap that
  every probe-based finding (F-2, F-3, H-13) currently lives with.

- **Best-of-5 sampling with human-validated rejection.** *Replication cost*:
  trivial. *We'd plausibly run this*: no — orthogonal to our pipeline.

## Approaches & framings

- **Compiled transformers as a falsification harness for interpretability
  methods.** Reframes interpretability evaluation from "does the explanation
  feel mechanistic" to "does the method recover circuits where the
  ground-truth mapping is known." Intersects our F-2/F-3/H-13 framings: every
  one of them currently has *no* ground-truth test, only correlational
  evidence on natural-trained LMs. TracrBench is the cheapest available
  oracle.

- **Distinguishing "method works on trained natural LMs" from "method works
  on a mechanistic circuit."** Our entire pipeline assumes a probe that
  predicts correctness *is* picking up computation. TracrBench makes this
  assumption testable.

## Datasets & benchmarks

- **TracrBench** — 121 RASP programs + corresponding compiled
  transformer weights (Tracr-compiled). Open-source (companion repo expected;
  authors are in the Tracr ecosystem). *Applicable*: yes, but only as a
  probe-validation oracle — not as a substitute for MATH-500. The compiled
  models are toy (single-digit layers, discrete-symbolic activations,
  no natural-language training distribution), so any positive result on
  TracrBench upper-bounds a probe's *floor*, not its ceiling on Qwen-2.5.

## Implementation details worth capturing

- 121 programs total: 64 manually written + 57 LLM-generated and
  human-validated, drawn from a 101-program test bank where GPT-4-turbo
  solved only 57 (56% pass rate with 20-shot + best-of-5).
- RASP primitives: `select`, `aggregate`, `make_x` operators with default
  threshold = 2 (visible in citation snippets); programs span sequence-level
  primitives like max-find, count, sort.
- All programs compiled through Tracr's RASP→weights pipeline — meaning each
  has a fully-known head and MLP layout.
- Programs come with difficulty annotations and a complexity histogram (from
  the figure references `difficulty_histogram.pdf`, `programs_complexity.pdf`,
  `score.pdf`, `success_rate.pdf` in the PDF metadata).

## Replicable intermediates

- **None against the paper's headline claim directly** — the paper's headline
  is "GPT-4-turbo solves 57/101 RASP programs," which we have no incentive to
  re-test.
- **Cross-check against our F-2 / F-3 / H-13 using TracrBench as oracle**:
  download the released TracrBench models, run `numpy`-only mass-mean DoM
  fitting on the residual stream of each binary-output program, compute
  cos(DoM, Tracr's known ground-truth feature axis). Pure CPU, ~1 day work.
  Cached NPZs not needed; this is a fresh small-scale extraction.
